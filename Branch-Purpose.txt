We want to examine new features/better features

To properly capture market regimes we need to capture volatility/variance, trends, and second order metrics, as well as order flow, and liquidity.

Features that are good for this:
VARIANCE FEATURES
- Realized Variance of rolling midprices at fixed time intervals for a fixed time window
- Volatility of Volatility, Calculated With the feature processor from incoming snapshots. Needs boot up time.
- Spread Volatility, STDEV of spread over the same setup as midprices
- Directional Volatility, Separate vol for positive/negative returns. IE have + dir and - dir vol

---
Data needed for these ^^^ . For Realized Variance we need **Rolling Midprices** (these will be updated fixed interval for feature input snapshots)
    For vol of vol we need to store the last 30-60 seconds of Realized Variance data points. (if 0.5 second snapshot, then 60-120 data points)
    For spread Volitlity we need **Rolling Spreads** (these will be updated fixed interval for feature input snapshots)
    For Directional Volatility we need **Rolling Midprices** (these will be updated fixed interval for feature input snapshots)
    
    in summary, we need rolling_midprices, rolling_spreads, and store our realized_vars in a rolling queue
---

DIRECTIONAL FEATURES
- Mean Log Return
- Order Flow Imbalance --> Needs to use sizes of orders, not just numbers
    - Need a struct, Bid Volumes and Ask Volumes as well as Bid TS and Ask TS
- Aggressor Bias/Ratio
- EMA of midprice over whole window versus over half window (ratio, norm diff, etc)
- Midprice Deviation from EMA
- Reversal Rate (already implemented)

---
for mean log return we can use the rolling midprices and update this at the same time as realized variance
for Order Flow Imbalance we need to store our bid volumes and ask volumes in a rolling queue, as well as the timestamps corresponding to each order
    - on process add we need to add the volumes to the rolling_queues and the timestamps to the rolling timestamps.
    - we will also store the current sum for both sides. When we want to get snapshot, we will evict the timestamps/volumes outside the current timestamp.
for Aggressor Ratio we have to store out trade volumes in a rolling queue, as well as timestamps corresponding to each trade
    - on process trade we need to add the amounts to the rolling queues and timestamps to the rolling timestamps.
    - we will also store the current sum for both sides. When we want to get snapshot, we will evict the timestamps/volumes outside the current timestamp.
For EMA of price we can use the rolling midprices and update this at the same time as realized variance
for Midprice Deviation from EMA we can use the rolling midprices and update this at the same time as realized variance

    in summary, we need rolling_midprices, a OrderFlowTracker object and an TradeFlowTracker object

LIQUIDITY FEATURES

    - BID AND ASK SIDE
